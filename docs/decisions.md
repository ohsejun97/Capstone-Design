# 설계 결정 기록 (Decision Log)

캡스톤디자인II — 에이전트 오케스트레이션 플랫폼으로 전환하면서 내린 구조 결정을 남긴다.
각 항목은 **결정 / 이유 / 검토한 대안 / 상태** 순서로, 면접에서 "왜 이렇게 했나요?"에 바로 답할 수 있는 길이로 쓴다.

상태 값: `확정` · `보류` · `대체됨(→ D-xxx)`

## D-001. 프로젝트 방향: 도메인 무관 플랫폼 + 의료 시나리오 하나로 검증

- **결정**: 구조(도구 플러그인, LLM 어댑터, 오케스트레이션)는 도메인에 묶이지 않게 만들고, 시연·평가는 의료 시나리오 하나로 깊게 한다.
- **이유**: 시나리오 없는 범용 플랫폼은 무엇을 해결했는지 증명할 수 없다. 반대로 시나리오에 구조가 묶이면 재사용성을 보여줄 수 없다. "의료 시나리오로 검증했고, 도구만 바꾸면 다른 도메인에도 쓴다"가 두 요구를 함께 만족한다.
- **검토한 대안**: 도메인 특화 앱(재사용성 증명 불가), 순수 범용 프레임워크(문제 정의 부재).
- **상태**: 확정 (2026-10-08)

## D-002. 시연 도메인: 보류 — 처방 안전성(B) 우선 검토

- **결정**: 도메인은 Phase 1 종료(2026-10 말)까지 확정한다. 현재 1순위는 처방 안전성 검토(약물상호작용·약물유전체)이고, 종양 치료 의사결정 보조(A)는 B가 안정된 뒤 확장 후보로 둔다.
- **이유**:
  - Phase 1은 도메인과 무관한 뼈대라 결정을 미뤄도 막히지 않는다. 도메인은 11월의 RAG 소스와 평가셋에만 영향을 준다.
  - B는 정답이 명확해(CPIC 권고, DDInter 상호작용 등급) 평가셋을 자동 채점할 수 있고, 공개 소스로 짧은 기간에 만들 수 있다.
  - B는 의료 지식 부담이 낮다. 이 프로젝트가 보여주려는 것은 "도메인 전문가가 아니어도 시스템을 끝까지 만드는 역량"이다.
- **검토한 대안**: A 종양(서사는 강하지만 의료 지식 요구가 커 일정 위험), C 신약 후보 탐색(기존 DTI의 연장이라 차별성 약함).
- **상태**: 보류 (2026-10-08, 기한 2026-10-31)

## D-003. 서비스 분리: Django(웹) + FastAPI(에이전트)

- **결정**: Django는 UI·인증·API 게이트웨이를, FastAPI는 에이전트 실행과 모델 추론을 맡는 별도 서비스로 둔다. 둘은 Compose 내부 네트워크에서 HTTP로 통신한다.
- **이유**: 인증·세션·관리 화면은 Django가 기본 제공하고, 에이전트 추론은 비동기 I/O와 긴 실행 시간이 특징이라 성격이 다르다. 분리하면 추론 서비스만 따로 재시작·확장할 수 있고, 웹 쪽 장애가 추론에 번지지 않는다.
- **검토한 대안**: FastAPI 단일 서비스(인증·관리 화면을 직접 구현해야 함), Django 단일 서비스(동기 요청 처리 중 긴 LLM 호출이 워커를 점유).
- **상태**: 확정 (2026-10-08)

## D-004. 배포: Docker Compose (K8s는 Tier 3)

- **결정**: AWS EC2 단일 노드에 Docker Compose로 배포하고, Nginx를 리버스 프록시로 둔다. 기존 K8s 매니페스트는 `deploy/k8s/`에 보관만 한다.
- **이유**: 노드가 하나일 때 K8s는 스케줄링·자가 치유의 이점이 없고 운영 비용만 늘어난다. 매니페스트를 보관해 두면 수평 확장이 필요해지는 시점에 옮겨 갈 수 있다.
- **검토한 대안**: K8s(kind/k3s 포함) — 일정 여유가 있을 때 로컬 시연만 고려.
- **상태**: 확정 (2026-10-08)

## D-005. LLM 호출: 어댑터 한 겹 + 외부 LLM에는 공개 데이터만

- **결정**: LLM 호출은 공통 어댑터 인터페이스 뒤에 두고, 기본 구현은 Groq로 한다. 외부 LLM API에는 공개·합성 데이터만 보낸다.
- **이유**: 실제 환자 데이터는 외부 서비스로 전송할 수 없다(자격 인증 데이터셋 이용 약관, 병원 개인정보 규정). 어댑터가 있으면 병원 환경에서는 구현체만 로컬 모델로 바꿔 같은 파이프라인을 쓸 수 있다. 테스트에서는 fake 구현으로 네트워크 없이 그래프를 검증한다.
- **검토한 대안**: 특정 SDK 직접 호출(교체 시 호출부 전체 수정 필요).
- **상태**: 확정 (2026-10-08)

## D-006. 도구 구조: 공통 인터페이스 플러그인, DTI는 플러그인 하나로 강등

- **결정**: 도구는 공통 인터페이스(이름, 설명, 입력 스키마, 실행 → 결과·근거·오류)로 레지스트리에 등록한다. 기존 DTI 모델(SaProt-650M + ft-ChemBERTa + MLP)은 삭제하지 않고 플러그인 하나로 둔다. 인터페이스 세부 정의는 구현 전에 별도로 확정한다.
- **이유**: 도구를 추가·제거해도 에이전트 그래프를 고칠 필요가 없어야 도메인 무관 구조(D-001)가 성립한다. 결과에 근거(evidence) 필드를 두면 평가 단계에서 환각 여부를 검사할 수 있다.
- **상태**: 확정 (방향), 인터페이스 세부는 미정

## D-007. EC2에서 DTI 플러그인 비활성화

- **결정**: 배포본(EC2, CPU)에서는 DTI 플러그인을 끈다. 로컬 GPU에서 동작하는 시연은 짧은 영상 또는 GIF로 남긴다.
- **이유**: SaProt-650M은 CPU 인스턴스에서 실사용이 가능한 지연 시간이 나오지 않고, GPU 인스턴스는 학생 예산을 넘는다. 설정 하나로 플러그인을 끄고 켤 수 있다는 것 자체가 D-006 구조의 시연이 된다.
- **검토한 대안**: 로컬 GPU 머신을 원격 워커로 연결(네트워크·보안 구성 부담), 사전 계산 결과만 서빙(임의 입력 불가).
- **상태**: 확정 (2026-10-08)

## D-008. 저장소 재배치 원칙

- **결정**: `services/web`, `services/agent`, `deploy/`, `evals/`, `research/` 구조로 옮긴다.
  - 이동은 `git mv`로 하고 기능 변경과 섞지 않은 단독 커밋으로 한다. 커밋마다 기존 테스트와 CI 통과를 확인한다.
  - `research/`(Phase 1 학습 실험 자산)는 읽기 전용으로 두고 내부 스크립트 경로는 수정하지 않는다.
- **이유**: 이동과 수정이 한 커밋에 섞이면 리뷰와 되돌리기가 어렵다. 실험 자산은 재현성이 생명이라 경로를 건드리지 않는다.
- **상태**: 확정 (2026-10-08)

- **이유**: 먼저 지우면 동작하는 UI가 없는 기간이 생긴다.
- **상태**: 확정 (2026-10-08)

## D-010. 범위 관리: Phase 1은 Tier 1만

- **결정**: Phase 1(10월)은 Tier 1(Django, FastAPI, PostgreSQL, Compose, EC2, Nginx, GitHub Actions)만 다룬다. 기존 MLflow는 Compose 선택 프로필로 뺀다. Tier 2(RAG, Celery, 트레이싱, MCP)는 Tier 1이 안정된 뒤에만 한다.
- **이유**: 1인 개발로 일정이 제한돼 있어, 이미 만들어 둔 것을 전부 살리려 하면 Tier 1이 늦어진다.
- **상태**: 확정 (2026-10-08)
